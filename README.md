# Make как единая точка входа

Проект демонстрирует, как упаковать хорошие практики разработки в воспроизводимые `make`-таргеты: управление виртуальным окружением, проверку зависимостей, статическую типизацию, форматирование кода и их композицию в единый пайплайн.

## Структура

```
makeenv/
├── Makefile                # единая точка входа
├── requirements.txt        # runtime-зависимости
├── requirements-dev.txt    # инструменты для проверки качества
├── scripts/
│   └── check_imports.py   # скрипт анализа импортов
└── src/
    ├── app.py             # точка запуска (использует requests)
    ├── service.py         # модуль с несколькими зависимостями
    ├── calc.py            # пример с аннотациями типов
    └── example.py         # пример форматирования кода
```

## Последовательность действий (ручной режим, до Make)

```bash
# 1. создать окружение
python3 -m venv .venv

# 2. установить зависимости
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt

# 3. запустить приложение
.venv/bin/python src/app.py

# 4. проверить, что все импорты объявлены в requirements.txt
.venv/bin/python scripts/check_imports.py src requirements.txt

# 5. статическая проверка типов
.venv/bin/mypy src

# 6. проверка стиля (без изменений файлов)
.venv/bin/ruff check src

# 7. автоформатирование (изменяет файлы)
.venv/bin/black src
```

## Автоматизация через Make

| Таргет               | Что делает                                              |
|----------------------|---------------------------------------------------------|
| `make venv`          | создаёт `.venv/` через `python3 -m venv`                |
| `make install`       | устанавливает все зависимости в `.venv/`                |
| `make run`           | запускает `src/app.py` через `.venv/bin/python`         |
| `make check-requirements` | сравнивает импорты в `src/` с `requirements.txt` |
| `make typecheck`     | статический анализ типов через `mypy`                   |
| `make lint`          | проверка стиля через `ruff` (только читает, не правит)  |
| `make format`        | автоформатирование через `black` (изменяет файлы)       |
| `make check`         | запускает `typecheck` + `check-requirements` + `lint`   |
| `make clean`         | удаляет `.venv` и кеши инструментов                     |
| `make help`          | выводит список таргетов                                 |

### Быстрый старт

```bash
make install   # однократно: создаёт окружение и устанавливает пакеты
make run       # запустить приложение
make check     # полная проверка качества
make format    # автоформатирование
```

## Логика решения

### 1. Управление окружением (stateless-подход)

Ключевая проблема: `source .venv/bin/activate` не работает в Makefile, потому что каждая строка таргета выполняется в отдельном shell-процессе. Состояние активации теряется между строками.

Решение — использовать явные пути к интерпретаторам:

```makefile
PYTHON := .venv/bin/python
PIP    := .venv/bin/pip
MYPY   := .venv/bin/mypy
```

Вызов `.venv/bin/python` гарантирует использование именно проектного окружения вне зависимости от того, что активировано в терминале. Это не "повезло" — это детерминированный выбор бинарника.

### 2. Проверка зависимостей (`check-requirements`)

Скрипт `scripts/check_imports.py` анализирует все `.py`-файлы в `src/` через модуль `ast` (без исполнения кода), извлекает имена верхнеуровневых импортов, фильтрует stdlib и встроенные модули, затем сравнивает с пакетами из `requirements.txt`.

Учтена неоднозначность маппинга `import_name → package_name` (например, `sklearn` → `scikit-learn`, `PIL` → `Pillow`). Для известных случаев есть словарь `IMPORT_TO_PACKAGE`. Решение приближённое — как и указано в условии задачи.

Разделение на `requirements.txt` (runtime) и `requirements-dev.txt` (инструменты) подчёркивает, что `mypy`, `black`, `ruff` не являются зависимостями приложения.

### 3. Проверка типов (`typecheck`)

`src/calc.py` содержит корректно аннотированный код:

```python
def add(a: int, b: int) -> int:
    return a + b

result: int = add(2, 3)   # правильно: int + int
```

Изначально в задании показывалась ошибка `add(2, "3")` — передача строки вместо `int`. `mypy` обнаруживает это статически. Код исправлен, `make typecheck` завершается без ошибок.

Имя таргета `typecheck` не зависит от инструмента — можно заменить `mypy` на `pyright` или `pytype`, не меняя интерфейс.

### 4. Проверка стиля (`lint` / `format`)

`src/example.py` — пример правильно отформатированного кода (после применения `make format`):

```python
def foo(x, y):
    return x + y
```

До форматирования код мог выглядеть как `def foo( x,y ):\n return x+y`. Инструменты разделены по назначению:
- `lint` (`ruff check`) — только **читает**, сообщает о нарушениях, не изменяет файлы. Используется в CI.
- `format` (`black`) — **изменяет** файлы. Запускается вручную перед коммитом.

### 5. Граф зависимостей таргетов (`check`)

```makefile
check: typecheck check-requirements lint
```

`make check` — составной таргет, который запускает три независимые проверки последовательно. Это демонстрирует, что Make управляет не просто командами, а **связями между действиями**. Каждый из трёх таргетов можно вызвать отдельно; `check` — это их декларативная композиция.

Граф зависимостей:

```
check
├── typecheck  → install → venv
├── check-requirements → install → venv
└── lint       → install → venv
```

Make автоматически не дублирует `install`, если он уже выполнен (через файловые маркеры или потому что `.venv` уже существует).

## Чистота репозитория

После `make install` / `make check` / `make format` в `git status` не появляются новые файлы:

- `.venv/` — покрыт `.gitignore` на уровне репозитория
- `__pycache__/`, `*.pyc` — покрыты `.gitignore`
- `.mypy_cache/`, `.ruff_cache/` — покрыты `.gitignore`

Это обеспечивает воспроизводимость: клонирование + `make check` всегда даёт одинаковый результат.
